# MY SPACE 정책·구조 기준 — 2026-10-09

이 문서는 확정 정책과 공통/역할별 책임의 기준이다. 실행은 LOCAL_SETUP.md, 상세 DB/API 계약은 CODEX_HANDOFF.md를 참고한다. 실제 운영 연결 완료와 정책 확정을 구분한다.

## 사용자 상태와 공통 기능

| 상태 | 이용 가능 범위 | 다음 행동 |
|---|---|---|
| 비로그인 | 공개 생성팀 탐색 | Google/Naver 로그인 |
| 승인 대기 | 본인 인증·승인 상태 확인 | NASA 이메일 인증 또는 운영팀 확인 대기 |
| 승인된 참가자 | 프로필·대원 탐색·받은/보낸 관심·동의 기반 이메일 | 프로필·연락 설정 |
| 승인된 팀 오너 | 참가자 공통 기능 + 확인된 소유 팀의 모집 관리 | 모집글 상태 확인 후 저장 |

팀 오너도 참가자다. 오너 전용 기능은 확인된 팀 소유 관계로 추가된다. role 쿼리나 브라우저 저장값은 실제 권한 근거가 아니다. 네 역할 선택은 비공개 review 화면에서만 사용한다.

인증 상태: required → email_pending → review_pending → 운영팀 승인. 만료·추가 확인·거절은 별도로 표시한다. 검증된 소셜 이메일이 이미 승인된 적격 참가 기록 1명과 유일하게 일치하면 자동 계정 연결한다. NASA 이메일 입력만으로 승인하지 않으며, 이메일 소유 인증은 허브 이용 승인·보호자 확인·팀 연락 동의를 대신하지 않는다.

## 관심 대화 — 5일 미응답 자동 종료 확정

- 최초 관심 메시지를 포함해 시작자 3회, 답변자 2회. 번갈아 최대 5개 메시지, 각 50자.
- 동일 행사·동일 두 참가자 사이에 최대 3개 대화, 동시에 활성 대화 최대 1개.
- 팀 대상 관심도 실제 수신 팀 오너의 participant_id로 계산한다. 팀/대원 경로를 바꾸거나 발신자를 바꿔도 같은 제한이다.
- **마지막 메시지 시각부터 5×24시간(120시간)이 경과하면 expired로 자동 종료한다.** 답변이 오면 마지막 메시지 시각과 기한을 다시 계산한다.
- 5개 메시지를 사용하면 completed로 종료한다. 이미 종료된 대화에는 추가 답변을 저장하지 않는다.
- 종료된 기록·메시지·사용한 대화 횟수는 보존한다. 전체 3개 한도에 여유가 있을 때만 새 대화를 시작한다. 대화 종료는 팀 가입·거절·이메일 동의 철회를 뜻하지 않는다.
- 참가자 seeking/paused/completed 및 팀 모집 상태는 새 관심의 허용을 결정한다. 기존 활성 대화는 5일 기한 안에서 유지된다. 이메일 연락은 수신 동의로 별도 판단한다.

상태 전이: active → completed(메시지 5개) 또는 active → expired(마지막 메시지 후 120시간). 검토 화면은 목록 조회·새 요청·답변 시 상태를 계산하고 화면을 열어둔 동안 1분 간격으로 갱신한다. 브라우저를 닫아도 다음 조회 시 과거 기한을 기준으로 종료한다.

**실제 운영 서버 연결 시** 서버 UTC 시각을 사용하며 목록 조회/새 대화 생성/답변 저장 트랜잭션에서 만료를 먼저 반영해야 한다. 동시에 새 요청이 들어와도 만료 처리·활성 1개·전체 3개·메시지 저장을 하나의 원자적 경로에서 검사한다. 브라우저 시계나 타이머만으로 실제 제한을 보장하지 않는다. 현재 실제 관심 API/DB 연결은 미완료다.

## 연락 수신 동의 — 팀에 연락하면 팀 오너에게 전달

| 연락 경로 | 실제 수신자 | 최신 수신 동의 |
|---|---|---|
| 팀 카드에서 이메일 | 확인된 팀 오너 참가자 | 오너 프로필의 ‘대원에게 이메일 받기’(peerEmailOptIn) |
| Team Owner가 대원 카드에서 이메일 | 해당 대원 | ‘Team Owner에게 이메일 받기’(emailOptIn) |
| 대원이 대원 카드에서 이메일 | 해당 대원 | ‘대원에게 이메일 받기’(peerEmailOptIn) |

팀은 이메일 계정이 아니다. 별도 팀 수신 동의를 생성하지 않는다. 오너 미연결·수신 동의 미확인 상태는 이메일을 허용하지 않는다. 팀 소유자가 변경되면 최신 확인된 수신자를 다시 조회한다. 기존 관심 대화의 수신자와 접근권한은 새 오너에게 자동 이전하지 않는다.

관심 대화는 이메일 수신 동의와 독립적이다. 이메일 발송 시 수신 동의와 발송자의 이메일 공개 동의를 다시 검사한다. 발송 서비스의 검증된 From과 서버에서 확인한 발송자의 Reply-To를 사용한다. 외부 답장에서는 상대 주소도 공개될 수 있다. 본문·외부 답장은 허브에 저장하지 않고 발송 메타데이터만 기록한다.

## 코드 책임과 공통/특이점

| 파일 | 책임 | 공통/역할/검토 구분 |
|---|---|---|
| hub-policy.js | 대화 횟수·5일 만료·수신 동의 판단 | DOM 없는 공통 순수 함수, Browser/Node 공용 가능 |
| match-catalog.js | 역할·Challenge·주제 기준표, 빈 상태 생성 | 공통 기준 데이터, 검토 계정 없음 |
| auth.js | 실제 세션 조회·인증 API 요청 | 공통, 주소 설정 전에는 전송하지 않음 |
| approval-flow.js | 인증·승인 상태별 문구와 다음 행동 | 공통 상태 표현 |
| workspace-ui.js | 참가자/오너 메뉴와 화면 전환 | 역할별 표시 차이 |
| match.js | 목록·프로필·모집·연락 UI 연결 | 아직 일부 역할별 폼이 함께 있음, 기준 데이터/검토 저장소는 외부 위임 |
| interest-threads.js | 같은 공통 정책으로 관심 카드·답변 표시 | 공통 카드, 현재 검토용 저장소에 연결 |
| preview.js | 네 역할과 승인 단계의 검토 모드 | review 전용, index.html에서는 로드하지 않음 |
| review-store.js | 예시 계정·예시 대화·검토용 localStorage·이전 검토 기록 변환 | review 전용, 실제 운영 데이터 저장소 아님 |
| auth-backend/server.mjs | OAuth·세션·이메일 인증·운영자 승인 | 로컬 서버, 운영자 권한을 서버에서 검사 |
| auth-backend/data-tools.mjs | 등록 대조·공식 생성팀 import | 원본 읽기와 로컬 관리 DB 쓰기를 분리 |

match.js는 UI 조율 역할을 유지한다. 프로필/모집 폼·상태 선택의 일부 리뷰 분기는 남아 있지만 예시 계정과 예시 대화 데이터는 review 전용 모듈로 이동했다. 실제 DB 어댑터 연결 전에 남은 UI 저장 흐름을 서버 API에 교체해야 한다.
